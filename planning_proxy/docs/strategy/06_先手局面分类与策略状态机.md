# 先手局面分类与策略状态机

## 这份东西解决什么问题

我们不让策略层直接猜 `v / h / w`。策略层只做一件事：收到当前壶面后，立刻给出唯一的离散判断：

```text
这是什么局面 → 这一手优先做什么 → 希望把壶面变成什么局面
```

随后才由粗代理缩小路径，再由严格 PhysX 搜索具体出手参数。这样“人类战术”与“连续物理求解”是解耦的：前者可解释、可改；后者负责真的打得到。

本文件目前只处理 **一局中的先手方**，即全局第 1、3、5、7、9、11、13、15 手（代码的 `shot_index=0,2,...,14`）。它不根据总比分、当前局数、冰况或扫冰作决定；这些需要在上层比赛策略补充，不能假装已经由本状态机解决。

## 输入和输出

输入是场上仍有效的壶：

```json
{"index": 3, "owner": "self", "x": 2.28, "y": 4.70, "enabled": true}
```

以及当前自己的全局手数 `shot_index`。每一次分类输出：

| 字段 | 含义 |
| --- | --- |
| `situation_type` | 当前属于哪一种局面，例如 `P3_ENEMY_HAS_CENTRE`。 |
| `strategy_type` | 这一手的离散任务，例如 `CLEAR_OR_OUTDRAW_TO_RETAKE_CENTRE`。 |
| `desired_state_type` | 这一手成功后希望转入的下一种局面。 |
| `target_opponent_index` | 优先处理的敌方壶；没有就为 `null`。 |
| `target_points` | 本次出手壶允许争取的落点槽，不是写死的唯一坐标。 |

代码入口是 [first_player_strategy.py](/D:/Desktop/冰壶/DCCourse/planning_proxy/first_player_strategy.py)。调用 `plan_first_player_turn(board, shot_index)` 时，上述三个状态字段已自动带在 `FirstPlayerPlan` 中。

若只想在收到壶面后立即看分类、而不启动任何物理模拟，可运行：

```powershell
cd D:\Desktop\冰壶\DCCourse
python planning_proxy\classify_first_player_state.py `
  --board planning_proxy\fixtures\rule_and_safety_scenarios_v1.json `
  --scenario-id 08_early_centre_guard --shot-index 2
```

输出会直接给出 `P2_PROTECTED_CENTRE_GUARD → AVOID_PROTECTED_GUARD_AND_DRAW_ANCHOR → P3_FIRST_INNER_ANCHOR`。比赛端不需要等到 PhysX 结束才知道战术类别；PhysX 只负责把这个类别落实成可提交的连续出手参数。

## 球形语言

- **中线守壶**：第一颗位于 `(2.375, 7.15)` 附近。它在自由防守区规则期内可限制对手把它撞出界；但它不是后方壶的绝对盾牌。
- **红圈锚 / 内圈壶**：按钮附近及红圈内、可成为得分层的壶。
- **错层红圈对**：两颗己方营内壶前后、左右错开，避免被一条直线同时处理。
- **边缘废球**：按本项目判定落在 `x∈[0.195,0.435]` 或 `x∈[4.315,4.555]` 的壶。它还在界内，但已不作为有效主战壶处理。
- **左右门**：营内壶前方左右两侧的保护槽。末手前只有“中心锚 + 中线守壶 + 左右双门”通过过本项目已有的对手最后一壶反击筛查。

### 判定顺序与失败回退

分类不是按“场上有没有敌壶”做二分。它按下列优先级读取壶面；前一项成立时，
不再被后面的“多留壶”愿望覆盖。

| 优先级 | 判定条件 | 本手主策略 | 成功后目标 | 严格 PhysX 找不到主策略时的回退 |
| --- | --- | --- | --- | --- |
| 1 | 前五手存在对方中线自由防守区壶 | 不撞离中线；绕开并 draw/外展。 | 己方第一锚或错层对。 | 不清该壶；只搜索不碰它的另一侧红圈/翼侧落点。 |
| 2 | 前五手存在对方普通自由防守区壶 | 只可推到边缘废球带，并尽量撞后滚入锚位。 | 第一锚或错层对。 | 若推边缘路径在任一摩擦序列犯规，放弃碰撞，直接 draw。 |
| 3 | 敌方营内壶是最近壶或正在多分 | 清、双飞、撞后滚、raise/promotion 或穿门 draw 中比较可达路线；不是只选直线打定。 | 己方重新成为最近壶，至少保留一个得分层。 | 若必清会撞散己方层，先选可合法的 outdraw / raise 修复最近壶；日志标 `tacticalGoalMet=false`，不伪称清壶成功。 |
| 4 | 己方最近但红圈壶少于两颗 | 补与已有锚前后、左右错开的第二层。 | 错层红圈对。 | 不向同一直线聚堆；转为另一侧槽或单侧护门。 |
| 5 | 第 4–5 颗己方中心层完整，敌方只是外圈/非计分壶 | 维持、外展或选择性处理，不强制清壶。 | 中心优势和下一颗可修复的角色。 | 保留最靠中心壶，宁可不打无效外圈壶；这不是“清场失败”。 |
| 6 | 第 6–8 颗有有效敌壶 | 先处理该威胁，出手壶同时滚进缺失的锚、红圈层或门位。 | 按存活己方壶数进入 `DEFENCE_TRANSITION`。 | 若联合目标不可达，先保规则合法、最近壶和现有得分层；不得把普通三角报成末手安全。 |
| 7 | 第 8 颗形成 G+A+L+R 四角色 | 把它送入当前真实终局的对手末手反击搜索。 | 仅反击搜索跨摩擦序列通过后，才是可提交终局。 | 搜索有反例、或尚未运行：输出“未验收候选/安全回退”，不能使用 `CERTIFIED` 或“守住”措辞。 |

其中 `(壶数)` 为 `ONE_OWN`、`TWO_OWN` 或 `THREE_PLUS_OWN`：不是固定要求留几颗壶，而是根据还在场的己方有效壶数选择“补第二红圈壶、补三角外壳，还是补双门”。

## 主路径和回退路径

主路径是：

```text
空场
→ 中线守壶
→ 第一红圈锚
→ 两颗错层红圈壶
→ 清敌方威胁同时维持中心优势
→ 按存活己方壶数补防御角色
→ 最后形成中心锚 + 中线守壶 + 左右双门
```

真实对局会被对手拆层，所以状态机不要求机械走完这条直线：

```text
敌方变成最近壶        → 先回到“夺回中心”
己方红圈层少于两颗    → 先回到“补错层红圈对”
有效敌壶被清空        → 直接补当前缺失的防御角色
第八手仍缺一侧门      → 补门后进入反击搜索；普通外壳不能伪装成已验证的终局防线
```

## 它与顶尖队伍资料、以及本地验证各自提供什么

公开 Team Gushue / 顶尖队伍资料提供的是**方向**：前半局建立前方压力与营内得分壶；对方把中路堵死时向两翼展开；对方壶被掩护时，比较清守壶、hit-and-roll、raise、穿门 draw，而不是认定“有守壶就安全”；在后手需要保留后手权时，blank 是正常分支。详见 [Team Gushue 公开战术树](05_Team_Gushue公开战术树_证据版.md)。

本项目自己的严格 PhysX 验证提供的是**硬门槛**：自由防守区规则、边缘废球带、红圈落点和末手反击搜索。离线通过的“双门基准模板”只说明该模板在限定父路线、局部扰动和摩擦序列中暂未发现反例；它**不**替代当前真实终局（含残留壶和碰撞后朝向）的反击搜索。公开战术资料不能替代这些几何与物理验证；反过来，物理求解器也不能自行决定“此局该进攻还是该 blank”。

## 实际执行顺序

```text
实时壶面
→ classify_first_player_situation
→ plan_first_player_turn
→ 粗代理给出可行连续路径区域
→ 严格 PhysX 在多条摩擦序列下精修
→ 规则检查
→ 若为第八颗候选：对每条实际终局壶面运行对手末手反击搜索
→ BESTSHOT
```

第八颗的严格回放报告会在每条摩擦序列下导出 `final_boards`（位置、owner、
可见 yaw）。将其中**一条**保存为 JSON 数组后，用以下命令验证；每个摩擦
序列终局都必须单独通过，才可给该连续出手参数最终放行：

```powershell
python planning_proxy\validate_final_defence.py `
  --board-json planning_proxy\runs\p8_seed_0_final_board.json `
  --direct-parents 5 --impact-parents 5 --physics-seeds 9 `
  --output planning_proxy\runs\p8_seed_0_reply.json
```

这里会把既有残留敌壶也纳入末手后的“谁最近”判断；`screenedSafe=true` 的含义
仅是该有限搜索下未发现反例。当前对局评估器会记录 P8 的模板命中与 `final_boards`，
但尚未自动串行执行这一步昂贵的逐终局反击搜索；没有该报告时，P8 只能标为
`reply-search-required`，不能作为“已防住”的胜率结论。

如果没有任何候选能通过严格物理和规则检查，当前代码应返回“无可提交候选”的事实，而不是捏造一条必成功路线。比赛端的安全兜底出手属于上层提交逻辑，必须单独设计和验证。

## 已验证的接线边界

这棵树现在不是只供离线报告阅读：

- `run_analytic_proxy.py --first-player` 会把完整 `firstPlayerPlan` 写进粗筛报告；
- `strict_refine.py` 会在每条摩擦序列上检查该计划的目标是否真的实现；
- `evaluate_vs_teammate_ppo.py` 中，规划代理作为**先手**时同样会调用这棵树，而不是退回旧的“见敌壶就清”。逐手日志会记录类型、策略、目标是否在严格 PhysX 下实现。

做过一局低预算接线烟测（每手 1 条摩擦序列、1 个精修区域）：前两颗分别得到并达成 `P1_EMPTY_SHEET → PLACE_CENTRE_GUARD` 和 `P2_PROTECTED_CENTRE_GUARD → AVOID_PROTECTED_GUARD_AND_DRAW_ANCHOR`。后续若严格层没找到达标候选，日志会写 `first_player_safe_fallback...` 且 `tacticalGoalMet=false`；这表示搜索预算或当前球形不足，**不表示策略已成功**。

因此当前结论是“分类—求解—严格验收的链路已通”，不是“这棵先手树已经证明能战胜对手”。后者仍需要用更大的精修区域、更多摩擦序列和多场对局统计验证。
