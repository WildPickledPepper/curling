## 实际调用及内存证据

本地 CP39 原生模块 SHA256：`7c31ced1773023e552391645e42040c9f3694d513805bc8b95ef0f8bc737bd38`；本次生产 Python 代码 SHA256：`1c7f1f9dd7498f4225740fca57cca85be7bc46845e92d08e554b9c142edce52f`。

本地 `PxcDiscreteNarrowPhasePCM`（RVA `0x284860`）在 `0x28487a` 调用自定义清空函数 `0x330f0`。Frida 只读记录 callId 1：调用前 `cachedSize=304`、序列化 manifoldCount=1；调用后 `cachedSize=0`、manifoldCount=0，缓存指针保留。反汇编中的 `0x332d1` 实际写入缓存长度零。条件只检查两个全局开关和 multi-manifold 标志，没有区分当前目标冰壶应否保留接触缓存。

Unity 目标冰壶的 `f70030`（convex-mesh PCM）入口是 `cachedSize=304`，实际调用 `f69978` 更新已有接触点，callId 132。本地对应更新函数 `0x29cbe0` 在这一帧没有调用；实际走了重新生成接触的分支，再调用 `0x29d550` 输出接触点。独立 Stalker 记录也显示本地进入生成分支。Stalker 的回栈不可靠，报告只使用它的调用点记录，输入输出证明来自单独的可靠 Interceptor 采样。

旧代码的来源见历史 ledger 的 C19/C20（2026-07-12）：根据当时 169 条缓存为空的采样，将每个窄相入口都清空 multi-cache 接入了生产。当前样例直接证明这一泛化不成立。历史样例通过，不能作为此无条件规则的机制证据。

## 差异如何传到最终状态

第 1382 步已生成目标冰壶与冰面的五个接触点。本地第 1383 步清空之前的缓存，与 Unity 更新之前的缓存，50 个接触计算字段逐位一致；两壶/冰面当前变换的 14 个字也一致。

第 1383 步走不同分支后，五个接触点仅 separation 字段不同，位置和法向仍逐位一致。第一点为：Unity `0xb4872cc4`（`-2.5178280793625163e-7`），本地 `0xb4838b50`（`-2.450201463943813e-7`）。其余四点详见机器报告。

将 Unity 原始 `f69978` 函数体原样提取，只添加内存和导出包装，再输入真实采样的旧接触点、变换矩阵和阈值。执行结果的 400 字节接触窗口与 Unity 实际出口完全相同。这直接验证了旧接触点的更新计算，不依赖参数试验猜测。

随后，目标冰面五条 normal constraint 每条仅偏移 `+36` 的修正项不同；header 的计算字段、其他 normal 字段、摩擦约束的有效计算字段一致。首轮目标冰面静态求解输出即不同。两冰壶之间的动态约束五轮冲量全部为零，并且不改变 solver body，故这一帧这七个差异不是碰撞冲量直接造成。

真实链条是：

```text
同一个旧接触缓存
→ 窄相入口：Unity 保留 / 本地清空（已确认分叉）
→ 更新旧接触 / 重新生成接触
→ 五个 separation 不同
→ 五条法向约束的修正项不同
→ 目标冰面静态求解输出不同
→ 目标冰壶完成状态的 qy、qz、vx、vz、wx、wy、wz 七个字不同
```

1383 是目标开始参与两壶求解的一步。本地目标第 1382 步完成时仍 sleeping，第 1383 步完成时 awake；Unity 此时也首次在本窗口静态求解块中出现目标 body。主冰壶的完成状态始终一致。

Unity 第 1384 步目标 PCM 入口缓存已经为零，与本地一致。现有 3000 步完成状态比较中，仅 1383 有差异，1384–3000 两壶的 P/Q/v/w 再次逐位一致。不能由完成状态重新一致推断中间所有未采样计算也已一致；此次尚未完整闭合触发下一步缓存失效的所有调用条件。
