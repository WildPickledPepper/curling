# 2026-10-02：修复 RigidID 生命周期与首碰 PCM 分叉

11005 在物理步 1022、角速度 setter ordinal 1023 的接触对排序与参考面分叉已修复。真实 Scene 调用现在产生 `active -> target`；以目标壶面 37 为参考面、活动壶面 17 为另一面，两个接触点的 **point / normal / separation 均与 Unity 逐 float 相同**。此前 1,023 次活动壶 P/Q 与 native angular setter 输出一致的验收仍通过。

## 修复依据与改动

没有交换最终接触结果，也没有写入指定 RigidID。新采样观察了 Unity `f71726` 构造、`f71727` 析构、`f71674` 回收及完整空闲/待回收编号数组；本地实际函数为 RVA `0x214bd0` / `0x214c50`。两侧构造函数都从空闲栈末端分配编号。

1. 生产默认启用 `eDISABLE_SIMULATION` 生命周期；重复停用已 inactive 的壶时，跳过此状态下无效的速度/睡眠 API。
2. Unity 启动时先注册壶，后注册冰面，随后停用 16 颗壶。本地此前在注册前就停用了壶，缺少初始编号池。现在通过正常注册、停用和一次全 inactive 的 Scene 步补齐这一历史。
3. 初始化回收顺序来自真实调用与编号池快照，作为固定场景的输入资产保存在 `local_simulator/assets/unity_startup_rigid_id_pool.json`。既有冰面在壶后注册，使高编号壶仍可进入回收栈。没有添加虚构 actor，也没有修改 native 二进制或编号内存。
4. 旧审计尾段漏掉 `UpdateState` 的出界停用。11001 / 11003 / 11010 的目标壶在 Unity 已被停用且编号已经可回收，旧审计仍把它们保留到下一次 Reset。审计现调用生产 `clear_out_of_play_stones()`，并执行下一物理步，使真实回收进入后续 Reset。判定使用本地位置和已恢复的场地边界，不读取 Unity 后续状态。训练样例原本已调用这项出界清理。

Unity 与本地非壶 actor 的数量不同，因此整数编号不必相同；按初始注册排名建立严格递增映射后，**12 个样本的 24 次目标/活动刚体构造，其分配编号、整个 freeIds 数组与 pendingIds 数组全部相同**。12 次实际首碰的角色顺序也全部相同。11005 的 Unity 活动/目标编号为 16/1，本地为 15/1。

这恢复的是该固定 Unity 场景已采到的初始化状态，尚未还原适用于任意场景的 Unity activation queue 排序算法。完整编号池验收覆盖 16 颗壶及记录的 12 枪生命周期；小型诊断 roster 仅投影此初始顺序。

## 当前剩余差异

接触几何闭合后，同一首碰帧的求解约束仍有差异。首条法向约束角向系数的第二分量：

| 字段 | Unity | 本地 |
| --- | --- | --- |
| 首条角向系数 Y | `-0.0295835193246603` | `-0.029583515599370003` |
| 首次求解后活动壶 angular Y | `-0.08141568303108215` | `-0.08308417350053787` |
| 首次求解后目标壶 angular Y | `-0.04194386303424835` | `-0.04497582092881203` |

两种 ABI 的约束头大小不同，比较时分别跳过 Unity 的 64 字节头与 native 的 80 字节头，不能将其中指针宽度差当作数值分叉。目标壶入口 quaternion/速度历史及 solver lockFlags 的既有差异也仍存在；上述角向系数差的具体计算来源尚未定位，不能凭这一轮终点改善归因。
