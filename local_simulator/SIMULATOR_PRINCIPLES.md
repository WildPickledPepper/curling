# 本地模拟器原理

## 1. 为什么只保留严格模拟器

交接包只保留一条模拟路径：`unity_front_half.py` 与 `unity_physx.py`。它保留真实起始朝向、逐 tick 摩擦、冰面网格、刚体接触与持久场景状态，因此能以 Unity 对齐为目标，而不是用近似模型换取速度。

```text
Unity 记录 ──> 协议状态与摩擦回放 ──> 持久 PhysX Scene ──> 终局误差
```

## 2. Unity 对齐路径的数据流

严格回放不从 Unity 拿碰撞后的答案，只使用碰撞前可观测输入：

```text
RESETPOSITION / RESETSTATE     BESTSHOT       A10 起始朝向       每 tick 摩擦
          │                       │                 │                 │
          └──────────────┬────────┴────────┬────────┴────────┬────────┘
                         ▼                 ▼                 ▼
               UnityFrontHalfSimulator：维护协议层壶状态
                         │
                         ▼
        PersistentPhysxFrontHalfScene：持久 actor / shape / ice mesh
                         │
          CurlingMotion 速度更新 → PhysX fixed step → 接触与求解
                         │
                         ▼
                 本地终局位置 ↔ Unity 终局位置
```

具体过程如下：

1. **还原场面。** `RESETPOSITION` 设置每颗壶的位置和静止速度；它不会把壶的朝向清零。
2. **还原出手。** `BESTSHOT` 给出出手速度、横向偏移和旋转输入；A10 事件提供该手真正进入刚体系统前的 active yaw。
3. **逐 tick 推进。** 从记录中读取 Unity 每一 tick 的摩擦随机量，调用恢复出的 `CurlingMotion` 更新速度，再以 Unity 固定步长推进 PhysX。
4. **由 PhysX 自己处理碰撞。** 石头-石头接触、冲量、切向摩擦和后续滑行均在本地持久 Scene 中生成；不写入 Unity 的碰撞后位置或速度。
5. **比较终局。** Unity 把当前手的最终棋盘状态随下一手 `GO` 交接；采样器将其标记为 `next_go_final_position`，审计器再计算两端终局距离。

## 3. 为什么必须使用持久 Scene

每手重新创建刚体看似简单，但与 Unity 的运行方式不同。Unity 在同一局中保留 Rigidbody、Collider 和部分内部接触历史；`RESETPOSITION` 只是移动壶，不等价于新建壶。

`PersistentPhysxFrontHalfScene` 因此在整个批次中保持：

- 同一批 actor、shape 与材质对象；
- 同一张从 Unity 捕获的冰面网格；
- 相同的壶编号和物理对象身份；
- 位置 reset 后仍保留的朝向语义。

这也是为什么严格验证需要逐手的 A10 yaw：位置相同不代表刚体初始状态相同。

## 4. 随机摩擦与 RNG

Unity 的全局 RNG 会随着运行顺序变化，因此“重新启动后用同一个输入再跑一次”不能保证得到同一条摩擦序列。处理方式分两类：

| 目标 | 做法 |
| --- | --- |
| 逐条严格复现 | 记录 Unity 每 tick 的摩擦随机量，并原样输入本地。 |
| 判断真实使用时的波动 | 对相同构型采样多次，比较落点分布而不是逐条配对。 |

当前严格误差表属于第一类；它证明给定同一上游输入时，本地物理是否对齐。它不替代第二类的分布测试。

2026-10-03 明确实际预测用途：调用者给出出手参数和完整起始场景，预测入口自行生成摩擦序列，不要求调用者提供 Unity 当次随机值。未知种子造成的单次落点差异可以接受；固定全部随机输入和调用调度后，后续计算应逐位一致。

自主生成还需单独核对每次抽取对应的控制器调用、抽取次数与消费顺序，以及碰撞、自然停止、墙碰停用后的分支。不能将 `friction_noises` 的已知长度当作预测入口的停止机制，也不能将普通物理尾段机械地转换为随机抽取。

帧间隔、timeScale、释放时的时间累计余量也是确定性输入。默认独立预测显式使用固定饱和帧时钟，并保留本地每手种子策略；不能将其推断为所有实机运行的未知时钟历史。随机输入和时钟输入都相同时才要求后续逐位一致。原 Scene 首碰 API 仍用于录制 setter 窗口回放，窗口终止不等于自主停止；完整浏览器 PlayerLoop、暂停/captureFramerate 和扫冰调度尚未纳入本次验收。

## 5. 朝向为什么是硬门槛

石头的朝向会影响碰撞时的接触几何和后续求解。由于 Unity 的 position reset 保留 yaw：

- active 壶：每一手从 A10 记录提取真实 yaw；
- fresh、此前未被使用的 target 壶：可使用 factory yaw `0`；
- 已经参与过历史碰撞的 target 壶：不能假定 yaw 为 `0`，必须采集真实朝向。

没有这些信息的报告只能说明趋势，不能宣称严格终局误差。

## 6. 坐标与物理约定

- 协议坐标使用冰壶比赛表面坐标；`unity_physx.py` 在内部转换到 Unity 原生 Y-up 坐标，避免镜像网格导致的接触差异。
- 冰面使用从 Unity 运行时捕获的三角网格，而非简单平面近似。
- 物理更新使用 Unity 固定步长；摩擦、速度和角速度的更新顺序遵循恢复出的运动控制逻辑。
- 默认生产路径使用本地 PhysX 真实接触；诊断用的 Unity 后态注入不属于交付路径。

## 7. 当前边界

### 已覆盖

- 非扫冰滑行；
- 单壶、擦碰、深擦、反旋、高旋和长距离偏移构型；
- 逐 tick 摩擦真值下的持久 Scene 碰撞回放。

### 未覆盖

- 扫冰请求何时生效、如何改变后续摩擦；
- 未记录 RNG 时的精确单次预测；

训练阶段关闭扫冰时，未覆盖的扫冰路径不会影响训练吞吐或非扫冰策略评估。

## 8. 如何正确使用验证结论

严格报告只有同时满足下列条件时，才能作为物理对齐证据：

1. `strictEndpointComparableCount == rowCount`；
2. `unreliableUnityEndpointSampleIds` 为空；
3. 报告保留原始 Unity samples、events、yaw manifest；
4. 对“实际接触=否”的行，不把它作为碰撞误差统计。

满足这些条件后，优先看被撞壶和出手壶的 RMSE、均值、最大值，并对最大误差构型单独复核，而不是只看一个总体平均数。
